# Strands Agents SDK — Capability Mapping for Tendril

This document maps **Strands Agents SDK** capabilities, as documented at
[strandsagents.com](https://strandsagents.com/docs/user-guide/quickstart/python/), to Tendril's
functional and non-functional requirements. It supersedes the speculative capability review in
[ADR-0001 Appendix A](./ADRs/0001-use-strands-agents-framework.md) with detail verified directly
against the live docs (Python SDK, fetched 2026-09-12) rather than reasoned from first principles.

Use this document to answer "does Strands already do this, and how?" before writing custom code.
For day-to-day coding conventions distilled from this review, see the
[`strands-agents` skill](../../.claude/skills/strands-agents/SKILL.md).

**Sources:** [Quickstart: Python](https://strandsagents.com/docs/user-guide/quickstart/python/)
and the concept pages linked from it (agent loop, tools, multi-agent patterns, interventions,
memory, context management, sessions, deployment, safety/security, observability, evals) —
fetched directly rather than taken from `llms.txt`'s summary, per `CLAUDE.md`'s "authoritative
Strands APIs" guidance.

---

## 1. Functional requirements

| Tendril requirement | Strands capability | Notes |
|---|---|---|
| **Model-driven dynamic orchestration** — no fixed execution order (ADR-0001) | The **agent loop**: reason → select tool → execute → repeat until `end_turn`. The model chooses tools per-turn; nothing is pre-scripted. | Confirms ADR-0001's core premise is exactly what the loop does natively — no custom scheduling code needed. |
| **Orchestrator ↔ specialist topology** (ADR-0012: agents-as-tools over `InvokeAgentRuntime`) | **Agents as Tools** pattern: `Agent(tools=[specialist.as_tool(...)])` or a custom `@tool` wrapping a remote call. Alternatives reviewed: **Swarm** (agents autonomously hand off to each other via `handoff_to_agent` — arguably closer to "specialists exchange information," but assumes all agents share one process/swarm, conflicting with specialists deployed independently on AgentCore); **Graph** (developer-defined nodes/edges, too rigid for genuinely emergent specialist selection); **A2A** (`A2AAgent` class wraps a *remote*, network-distributed agent as a tool over the Agent2Agent protocol — a native alternative to hand-rolling an `InvokeAgentRuntime`-calling `@tool`, worth evaluating if/when AgentCore exposes an A2A-compatible interface). | ADR-0012's choice stands: agents-as-tools is the only pattern compatible with "specialists keep independent AgentCore deployment." **Follow-up worth a look:** `A2AAgent` might let the orchestrator wrap each registry-declared specialist without hand-writing the `InvokeAgentRuntime` tool wrapper AF-03 currently plans — evaluate before implementing AF-03/WS-04's tool-binding code from scratch. |
| **Tool integration** ("tools are APIs", AF-03: each tool is a Lambda behind an API) | `@tool` decorator (function/class/module-based), plus **MCP tools** via `MCPClient` (stdio/HTTP/SSE transports, OAuth/IAM/custom-header auth, tool filtering, name-prefixing). Tools can be async, stream progress via `yield`, and access `ToolContext` (agent, tool-use id, `invocation_state`). | AF-03's "Lambda + API, template agent binds a registry `tools` list" is naturally a thin `@tool`-decorated HTTP-calling function per tool name — no framework gap. **MCP is a second option**: exposing each Tool API as an MCP server (stdio/HTTP) would let the template agent gain new tools by adding an MCP client, no new binding code per tool — a stronger fit for "genuinely swappable" than one bespoke `@tool` wrapper per tool if the tool count grows past the ~5 planned. |
| **Plan proposal → human approval (HITL)** (project-context.md §6.7, architecture.md §7.1) | **Interventions**: `Confirm(prompt)` action pauses before a tool call for human approval; the `HumanInTheLoop` handler wraps this with allow-lists, trust mode, an LLM risk classifier, and a custom `ask` callback (any channel — the callback is channel-agnostic). | Maps directly onto "propose plan → user approves" (architecture.md §7.1). **Target the web UI first**: `ask` resolves once the WebSocket-pushed approval prompt gets a reply via `POST /plans/{id}/approve` (ADR-0004) — WhatsApp is in scope long-term but deprioritized to a future backlog item (ADR-0001 refinement, 2026-09-12); don't build the WhatsApp callback before the UI one. |
| **Cross-invocation resume for HITL and the tracking loop** (ADR-0004/0012: Lambda, stateless, EventBridge-woken) | `HumanInTheLoop`/interrupts return `stop_reason="interrupt"` with an `interruptId`; the caller resumes a **later, separate invocation** by passing back an `InterruptResponseContent`. Combined with a **session manager** (`SnapshotSessionManager` + `S3Storage`/custom `Storage`), full agent state (messages, agent state, conversation-manager state) survives across Lambda invocations keyed by `session_id`. | This is the single most load-bearing finding: Strands' interrupt/resume + session snapshotting is **built for exactly this** ("stateless deployments... critical for serverless Lambda environments," per the docs). **Recommendation:** key the orchestrator's session_id to the `goal_id`; every EventBridge wake (a user reply, a follow-up due) re-creates the same `SnapshotSessionManager(session_id=goal_id, storage=...)` and the agent resumes exactly where it left off — no custom pause-state serialization needed in `app/orchestrator/`. |
| **Long-running outcome loop, quality/goal-satisfaction retries** (project-context.md: "owns a goal and drives itself to completion") | **GoalLoop** plugin: validates the agent's last response against a stated goal (natural-language judge or a programmatic validator function) and re-invokes with injected feedback until it passes, times out, or exhausts `max_attempts`. | A good fit for *within-turn* quality gating — e.g., "does this proposed plan actually address the stated success criteria?" — distinct from the *multi-day* EventBridge-driven resume loop (which is a session-resume concern, above, not a GoalLoop concern). Don't conflate the two. |
| **Memory — "remember everything about your garden"** (ADR-0001 action item 6) | `MemoryManager` + a `MemoryStore` (production: `BedrockKnowledgeBaseStore`). Auto-**injection** (fail-open, ephemeral `<memory>` block before model calls) and auto-**extraction** (background, every N turns or on a custom trigger) both configurable per store. Multi-tenant isolation via a `scope` parameter stamped on every write and applied as a retrieval filter. | Recommend `scope=f"{user_id}:{garden_id}"` per store — this *is* the multi-tenant isolation mechanism ADR-0001 asked for, not something to build separately. `writable=True` + `data_source_type="CUSTOM"` is the simplest write path (no S3 sidecar management). |
| **Bounded context over multi-week histories, pin the garden's vision/success criteria** (ADR-0001 action item 8) | `context_manager="auto"` composes `SummarizingConversationManager` (0.3 summary ratio / 0.85 compression threshold) + `ContextOffloader` (large tool results truncated to a preview + `retrieve_offloaded_content` tool). Pinning is available two ways: `context_manager="agentic"`'s `pin_context` tool (model-invoked, so pinning is a *model decision*), or the **Context Injector** plugin (`ContextInjector(callback, trigger="everyTurn")`) — deterministic, ephemeral, never persisted to history. | **Recommendation:** use `context_manager="auto"` for summarization/offloading, but pin the garden's vision + current success criteria via **`ContextInjector`**, not `pin_context` — the vision must never depend on the model remembering to pin it. `ContextInjector`'s own docs flag it as a prompt-injection surface, so any interpolated (non-static) content must be escaped. |
| **Structured Plan/Task output** (ADR-0011's OpenAPI schemas; architecture.md §2 domain model) | `structured_output_model=<PydanticModel>` on an agent call — works *in the same turn* as tool use; the agent executes tools, then formats the final answer to the schema. Malformed output raises `StructuredOutputException` rather than silently returning bad data. | Define `Plan`/`Task` as Pydantic models mirroring ADR-0011's OpenAPI `components.schemas` (ideally the same source of truth, not two hand-maintained copies) and request them via `structured_output_model` from the orchestrator's final "propose a plan" turn. |
| **Per-agent model choice** (ADR-0001: "right model for the job") | `Agent(model="global.anthropic.claude-sonnet-4-6")` (string) or a `BedrockModel(...)` instance with per-agent `temperature`/region/etc. 15+ providers supported (Bedrock default, Anthropic direct, OpenAI, Ollama, SageMaker, custom). | Confirms the registry's `model_id` field (ADR-0012) is a straight pass-through to `Agent(model=...)` in the template — no per-agent code branching needed. |

## 2. Non-functional requirements

| NFR | Strands capability | Notes |
|---|---|---|
| **Safety floor / guardrails** (ADR-0008: managed layer must never be the only defense) | `BedrockModel(guardrail_id=..., guardrail_version=..., guardrail_trace="enabled")` attaches a Bedrock Guardrail; a block surfaces as `response.stop_reason == "guardrail_intervened"`. Input redaction is on by default; output redaction is opt-in (`guardrail_redact_output=True`). A non-blocking "shadow mode" is possible via a custom hook calling `ApplyGuardrail` directly. | This *is* exactly what `agents/hello_agent/agent.py` already implements (PG-04) — confirms the existing pattern is the documented, correct one, not an approximation. |
| **PII handling** (ADR-0008: anonymize EMAIL/PHONE/NAME/ADDRESS) | **Not a Strands feature.** The docs are explicit that Strands "does not natively perform PII redaction" and point to Bedrock Guardrails' own PII entity masking (already ADR-0008's approach) or third-party libraries (LLM Guard, Presidio, AWS Comprehend) for *telemetry-layer* redaction (i.e., scrubbing traces/logs, not the model's input/output). | Confirms ADR-0008 put PII handling in the right layer already — nothing to change. If OTel trace export ever needs its own PII scrubbing (traces can capture full prompts), that's a separate telemetry-pipeline concern (OTel Collector `attributes/pii` processor), not an agent-code concern. |
| **Prompt-injection defense, tool-output trust boundary** (ADR-0008: "tag-based selective evaluation... don't evaluate system/tool/RAG content as user input") | **Trusted Message History** guidance: build message history from your own application, not from caller-shaped input; in Python, a **trailing tool-use block is executed directly without model reasoning** if present in resumed/loaded history — a real injection vector when history comes from an external source (e.g., a resumed session, a shared store). Mitigation: strip trailing `toolUse` blocks before passing loaded/external history to the agent. | Directly actionable for the orchestrator: since sessions are *resumed* from S3-backed snapshots (see HITL/resume row above), and `agents/registry`-driven specialists receive orchestrator-constructed input, apply the documented `strip_trailing_tool_use()` pattern wherever history could have been touched by anything other than the agent's own prior turn. |
| **Authorization / per-tenant access control** (beyond IAM's coarse per-role scoping) | **Cedar Authorization** intervention: policy-based, fail-closed (`permit` is opt-in, everything else denied), maps tool calls to `principal`/`action`/`resource`/`context`, supports hot-reload and rate limiting (`context.session.call_count`). | Not currently in any ADR — flagged here as a candidate for finer-grained, per-user authorization if/when Tendril needs it beyond IAM execution-role scoping (e.g., "this user's session may only call `weather`, not `notification`"). |
| **Observability** (ADR-0001 NFR table: OTel + X-Ray + CloudWatch) | Native OTel spans at 4 levels (agent → cycle → model invocation → tool), token/cache-usage metrics, `trace_attributes` for tagging `session.id`/`user.id`/custom tags. Exports via OTLP to any collector, or AWS ADOT/CloudWatch (`OTEL_SEMCONV_STABILITY_OPT_IN`, Transaction Search must be enabled). AgentCore has built-in CloudWatch Application Signals; Lambda does not (bring your own OTel setup). | Set `trace_attributes={"session.id": goal_id, "user.id": user_id}` on every agent construction — this is the load-bearing correlation key across the orchestrator's Lambda invocations and the specialists' AgentCore runtimes for one goal's full trace. |
| **Deployment target split** (ADR-0012: orchestrator on Lambda, specialists on AgentCore) | Lambda: a plain `def handler(event, context): return str(agent(event['prompt']))`, an official Strands Lambda Layer (`arn:aws:lambda:{region}:856699698935:layer:strands-agents-py{version}-{arch}:{n}`) to avoid bundling deps. AgentCore: `BedrockAgentCoreApp` + `@app.entrypoint`, mandatory `/invocations`+`/ping`, ARM64/ECR, `runtimeSessionId` (33+ chars) for session correlation. | Confirms both sides of ADR-0012's split map to first-class, documented Strands deployment paths — neither is a workaround. Use the official Lambda layer for the orchestrator to control cold start. |
| **Resilience / retry** | Automatic retry **only** for `ModelThrottledException` (exponential backoff, 6 attempts by default, configurable via `ModelRetryStrategy`). **Tool errors are never auto-retried** — they're returned to the model as an error result so *the model* can decide to retry/recover; a custom `Hook` (`AfterToolCallEvent.retry = True`) can force a mechanical retry instead. | Relevant to AF-03/WS-04: a failed specialist `InvokeAgentRuntime` call surfaces to the orchestrator's model as a tool error by default (model may retry a different specialist or give up gracefully) — decide explicitly whether that's sufficient or whether a `Hook`-based mechanical retry (per the documented `RetryOnToolError` pattern) is needed for specialist-call reliability. |
| **Testing model-driven behavior** (ADR-0001 action item 4; PG-07's hand-rolled eval script) | **Strands Evals SDK**: `OutputEvaluator` (rubric-graded), deterministic evaluators (`Equals`, `ToolCalled`, etc. — CI-friendly, no LLM judge cost), trajectory/tool-usage evaluators from OTel traces, `Experiment`/`Case` for versioned regression suites. **Red Teaming** (`strands_evals.experimental.redteam`): adversarial `guideline_bypass`/`system_prompt_leak`/`harmful_content`/`data_exfiltration`/`excessive_agency` attacks via strategies like `CrescendoStrategy`, scored 0–1 as breach/no-breach. | **Recommendation:** adopt `strands-evals` as the actual tool behind PG-07 and ADR-0008's eval requirements, rather than continuing to hand-roll `scripts/eval_guardrail.py`'s scenario list — deterministic evaluators cover the guardrail on/off-domain cases in CI at no LLM cost, and Red Teaming directly exercises the "prompt injection" and "off-domain" guardrail scenarios PG-07 already lists, with a structured report instead of print statements. Red Teaming's API is explicitly experimental — pin the SDK version. |
| **Multi-tenancy** (architecture.md §6.3: "memory/storage stores and DynamoDB keys scoped per user/garden") | Memory store `scope` (above), Cedar's `principal_resolver`/`context_enricher`, and `invocation_state` (a plain dict propagated to agents/tools/hooks in Graph/Swarm *without* entering the LLM prompt) as the general mechanism for passing `user_id`/`garden_id` through a multi-agent call without it leaking into model reasoning. | `invocation_state={"user_id": ..., "garden_id": ...}` is the one mechanism to standardize on for passing tenant identifiers through the orchestrator → specialist-tool → memory-scope chain consistently. |

## 3. What this confirms vs. refines in existing ADRs

**Confirms, unchanged:**
- ADR-0001's model-driven, no-fixed-order premise (the agent loop itself).
- ADR-0008's guardrail attachment pattern (`BedrockModel(guardrail_id=...)`) already matches the documented API exactly — `agents/hello_agent/agent.py` needs no correction.
- ADR-0008's PII-at-the-guardrail-layer decision — Strands has nothing to add or conflict with here.
- ADR-0012's agents-as-tools topology, and that both Lambda (orchestrator) and AgentCore (specialists) are first-class, documented Strands deployment targets, not a workaround.

**Refines (small corrections/additions, not reversals — see each ADR for its own append-only refinement note where one was warranted):**
- **AF-05 (memory & context):** pin the garden's vision/success-criteria via **`ContextInjector`**, not the `agentic` mode's model-invoked `pin_context` tool — deterministic beats "hope the model chooses to pin it." Memory scoping should use the store's native `scope` parameter directly (`scope=f"{user_id}:{garden_id}"`), not a bespoke isolation scheme.
- **WS-04/AF-03 (orchestrator ↔ specialist invocation):** evaluate the SDK's native `A2AAgent` class before hand-writing an `InvokeAgentRuntime`-calling `@tool` wrapper — it may remove custom code, if AgentCore's runtime can be reached over A2A.
- **AF-03 (tools):** consider exposing Tool APIs via **MCP** (stdio/HTTP) instead of one bespoke `@tool` per tool, if the tool count grows past the ~5 currently planned — new tools would need zero new binding code in the template agent.
- ~~**The orchestrator's cross-invocation resume**~~ — **done (Phase 7.5+, `docs/stories/tracker-scheduler.md`'s SR-01/02/03)**: `SnapshotSessionManager` keyed by `goal_id`, exactly as recommended here, wired into `_build_orchestrator_agent` and live-verified (session isolation across two goals, correct context retention across turns).
- **PG-07 / ADR-0008's eval requirement**: adopt `strands-evals` (deterministic evaluators + Red Teaming) as the implementation, rather than continuing to extend the hand-rolled `scripts/eval_guardrail.py`.
