# Stories — Epic: Coconut Plantation (Bramhangaon)

Take Tendril from an amateur-garden assistant to the tool that runs a real **105-palm coconut
plantation**, by onboarding the existing Bramhangaon coconut-tracking project and adding the
plantation-grade capabilities the garden model never needed. Requirements, priority and
dependencies below; design rationale and trade-offs are in
[`../coconut-plantation-roadmap.md`](../coconut-plantation-roadmap.md).

**Story format:** `As a <role>, I want <capability>, so that <benefit>` + Acceptance Criteria +
Tasks + Dependencies + Status. **Status legend:** ✅ done · ◐ partially done · ☐ to do.

> **Governance:** every story below is architecturally significant (new data access pattern,
> new component, new channel, auth, or crossing the project-context §11 commercial non-goal).
> Per [`../../CLAUDE.md`](../../CLAUDE.md), each needs a **human-approved ADR before code** — the
> ADR each story blocks on is named in its row and its Dependencies. Do not start a story's code
> until its ADR is accepted.

## 0. The model in one paragraph (read first)

Two layers with different jobs. **Plant layer = inspection/assessment log** (read-mostly): each of
the 105 palms accumulates a **date-wise history of photos and log entries** (status + notes) that
is append-only and never overwritten; there are essentially **no plant-specific activities**. **Garden layer = assessment + activity log** (where the work is):
every real intervention is garden-wide (humic acid, jivamrut, foliar spray, leaching, weeding).
The system rolls up the plant inspections into an **overall garden state**, suggests **garden-level
activities**, the owner accepts, and it tracks them to done with WhatsApp reminders, in Marathi.
Intercropping/irrigation/soil are **Garden-level context**, not separately tracked (no Crop
entity). A new **Supervisor** agent (an architecture candidate, pending its ADR) sits above the
existing orchestrator, owns the garden's standing goals and its own agenda; the orchestrator stays
the per-goal composer it is today.

**Decisions recorded (owner review, 2026-11-23):**
1. **Stake number is optional.** It is the farm's own physical label, unique *within a garden*
   when present, never generated by Tendril; `plant_id` stays the internal identity.
2. **Date-wise photos and logs are kept as history** per plant (append-only).
3. **A dedicated plant endpoint**: `GET /gardens/{gardenId}/plants/{plantId}`.
4. **Memory scope is per garden** (`garden:{garden_id}`), which is what the code does; the docs
   that said `{user_id}:{garden_id}` were corrected.
5. **WhatsApp comes after auth.** CP-09 (WhatsApp) now follows CP-11 (mobile-number auth +
   recipient mapping).
6. **Supervisor** is a new agent and an architecture candidate (CP-07).

## CP-02 — Bulk-add Plants (optional stake numbers)

**As an** owner, **I want** to create all 105 numbered palms at once, **so that** I don't add 105
plants by hand.

**Acceptance criteria**
- **`stake_no` is an optional Plant attribute.** It is the farm's own physical label, never
  generated by Tendril. `plant_id` (uuid) remains the internal identity, so a palm can exist with
  no stake number and a stake can be renumbered without rewriting the plant's history.
- When present, `stake_no` is **unique within the garden** (not globally); a second plant with
  the same stake number in the same garden is rejected.
- A bulk/numbered-range import creates Plants #1–105 under the Garden, each with variety
  (Kalpa Samrudhi D×T), stage, and its stake number.
- `createPlant` accepts an optional `stakeNo` and an optional `stage` (today `stage` is
  hardcoded to `"new"`).
- The 23 Tall are not created as main-crop plants (optional: created with a `border` flag).
- Idempotent: re-running does not duplicate a plant (guard on stake number when present).
- `listPlants` returns all plants in a block/grid-friendly order (stake number ascending, plants
  without one last), paginated, without one GetItem per plant photo (today's N+1).

**Tasks** — optional `stake_no` + per-garden uniqueness guard (e.g. a `GARDEN#{id}` /
`STAKE#{no}` lookup item written transactionally with the Plant); bulk-create path (reuse
`createPlant` write); OpenAPI update; tests; dev smoke test.
**Dependencies:** CP-01. **Blocking ADR:** covered by ADR-0032 (Accepted). **Status:** ◐ built +
unit/contract-tested (2026-11-23): optional `stakeNo` with a per-garden `STAKE#` lookup (409 on
duplicate), optional `stage`, `POST /gardens/{id}/plants/bulk` (idempotent, ≤200/call,
out-of-range numbers created but flagged), `listPlants` stake ordering + full pagination + one
`BatchGetItem` for photos, delete frees the stake number. Frontend shows "#74 Coconut".
**Open:** deploy + smoke test (bulk-add #1–105 in dev, re-run to confirm all 105 skipped).

## CP-03 — Plant history: date-wise photos + logs (data model + write path)

**As an** owner, **I want** each palm to keep a date-wise history of its photos and log entries,
**so that** I can see how a palm changed over time. *(This is the carried-forward gap: Tendril's
`Media` is keyed by random id with no dated per-plant query, and a plant links only one hero
photo.)*

**Acceptance criteria**
- A **history entry** is dated by its *observation date* (not upload time) and holds any of:
  one or more photos (Media), a status (`healthy|ok|watch`), and a note. A log entry with no
  photo is valid, and so is a photo with no note.
- A documented access pattern returns a plant's history **by date** (newest- or oldest-first)
  without a scan, e.g. sk `PLANTLOG#{plant_id}#{date}#{entry_id}` under the garden partition,
  or a sparse GSI (decided in ADR).
- History is **append-only**: writing an entry never overwrites or deletes earlier photos or
  logs. Corrections (e.g. moving a misfiled photo, CP-08) are recorded, not silent rewrites.
- The plant's latest status/photo is derivable cheaply (denormalized onto the Plant item on
  write) so `listPlants` doesn't read history.
- Backward compatible with the existing single hero-photo (`Plant.media_id`) behavior.

**Tasks** — ADR for the history key/entity (incl. the optional `stake_no` from CP-02); write
endpoint (e.g. `POST /gardens/{id}/plants/{plantId}/history`); migration-friendly (CP-04 writes
into it); tests.
**Dependencies:** CP-02. **Blocking ADR:** Plant history entity + access pattern. **Status:** ☐ to do.

## CP-04 — Migration script (DynamoDB + S3 + KB seed)

**As an** owner, **I want** a one-shot script that loads the whole existing archive into Tendril,
**so that** no history is lost and the agents start warm.

**Acceptance criteria**

- For each `…\<NN>\YYYY-MM-DD[_HHMM]_plant<NN>.jpg`: uploads the full-res image to MediaBucket and

- Resource names from env (`APP_TABLE_NAME`, `MEDIA_BUCKET_NAME`, KB names); no hardcoded ids/ARNs.
- Verification pass: per-plant photo counts and latest status match the current tracker before
  cut-over; archive kept as backup of record.

**Tasks** — script in a self-contained folder (own `requirements.txt`); filename-date parser (both
shapes); S3 + DynamoDB batch writes; KB ingest; dry-run + verify mode; run against `dev`.
**Dependencies:** CP-01, CP-02, CP-03. **Blocking ADR:** uses CP-01/CP-03 ADRs. **Status:** ☐ to do.

## CP-07 — Garden-state assessment + Supervisor agent

**As an** owner, **I want** the app to assess my whole block and propose the next garden-wide
activity on its own, **so that** I'm told what to do next instead of reading 105 records myself.

> **Architecture candidate (2026-11-23):** the Supervisor is a **new agent**, recorded as a
> *candidate* component in [`architecture.md`](../architecture/architecture.md) §3. It stays a
> candidate until its ADR is accepted; no code before then.

**Acceptance criteria**
- A **deterministic rollup** (plain code, Tracker-style, model-free) computes a compact garden-state
  summary (status counts, recurring symptoms, recent activity, context).
- A new **Supervisor** component (scheduled via EventBridge, its own agenda of standing checks)
  consumes the rollup and **owns the garden's standing goals**; when it decides to act it **submits
  a garden-scoped goal into the existing orchestrator** (which composes specialists as today).
- Reasoning that turns the rollup into an assessment + suggested activity lives in a **new
  garden-level specialist** (factory registry entry: prompt + guardrail, no new agent code) — or in
  the Supervisor itself; decided in ADR.
- Output is a block-level assessment + one suggested garden activity (CP-06); owner accepts → tracked.
- The orchestrator is **not** replaced; the Supervisor sits above it. Supervisor **agenda tasks**
  (internal checks/decisions) are distinct from operational garden activities (CP-06).
- ADR calls out the model choice for the Supervisor/garden specialist (reasoning-heavy; revisit once
  the Bedrock/Anthropic issue is resolved — Strands makes the model a one-line per-agent choice).

**Tasks** — ADR (Supervisor-over-orchestrator pattern; 2 rejected options: peer specialist only;
extend orchestrator); deterministic rollup; scheduled trigger; Supervisor loop + agenda entity;
garden specialist registry entry + prompt/guardrail; eval scenarios + tracing; dev smoke test.
**Dependencies:** CP-05 (inspections to roll up), CP-06 (activities to create). **Blocking ADR:**
Supervisor agent + garden-state assessment. **Status:** ☐ to do.

## CP-08 — Upload → auto-map to a plant

**As a** worker, **I want** a photo I upload to file itself to the right palm, **so that** I never
pick a plant by hand.

**Acceptance criteria**
- Vision reads the stake number; **high confidence + matches an existing plant's `stake_no` in
  this garden** → auto-file to that plant's history (CP-03), no prompt.
- **Low confidence / ambiguous / no readable stake** → one-tap confirm or pick the plant before
  filing. Plants without a stake number (it is optional, CP-02) are always picked by hand.
- **Reads outside the garden's stake range (CP-01 context) or clearly a new planting** →
  guarded auto-create, always flagged (a new number is more likely a misread than a real new
  palm).
- A cheap "move this photo to #NN" correction exists for the rare misfile.
- Vision never silently *assigns* identity on low confidence (data-integrity control).

**Tasks** — ADR (plant-identity / auto-map policy + confidence threshold); map-on-upload flow;
confirm + correction UI; eval scenarios for the vision read; dev smoke test.
**Dependencies:** CP-03. **Blocking ADR:** Auto-map / plant-identity policy. **Status:** ☐ to do.
